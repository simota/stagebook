# 本実装の構成

前提: 帳票の形は `docs/format-research.md` で決めた。この文書には構成の「決定と理由」だけを残す。構造そのものはコード（`src/`）を見ること。

## 決定一覧

### 1. 技術スタック: Vite + React + TypeScript、状態管理は Zustand

- 理由: 決め手は編集UIの複雑さ。並べ替えられる表、ドラッグで動かすステージ図、6種類の入力フォームが、1つの公演データを同時に書き換える。モックのような素のJSでは、どこを描き直すかの管理が編集画面1枚ごとに膨らむ
- 不採用:
  - 素のJS（モックの延長）: 上記の理由
  - Svelte: 素直に書けるが、並べ替えなどの既製部品が少ない
  - Canvas系ライブラリ（Konva など）でステージ図を描く: 印刷にはSVGが必要なので、編集用と印刷用で描画を2本持つことになる
- 代償: ビルド工程と依存パッケージを抱える（React, Zustand, dnd-kit, zod）
- 見直す条件: 編集画面がセットリストの表1枚で済むと分かった場合

### 2. 帳票は「公演データを受け取って描くだけ」のコンポーネントにする

- `sheets/` の各コンポーネントは公演データだけを受け取り、状態を持たない。編集中の右側プレビューと印刷で同じコンポーネントを使う
- ステージ図の編集画面も、印刷用のSVG描画（`StageSvg`）に選択枠とドラッグ操作を重ねて作る。描画を2本持たない
- 寸法はmm単位とステージ単位（幅160×奥行44）で持つ。画面に合わせた拡大縮小はCSSの `transform: scale` で行う

### 3. データモデル

```ts
type Show = {
  schemaVersion: 1;
  id: string;
  meta: { band; event; venue; date; slot; slotSec; contact };
  members: Member[];            // { id, name, part }
  items: SetItem[];             // kind で区別: song | se | mc | change | encore | memo
  stageParts: StagePart[];      // { id, type, x, y, rot, label, sub?, memberId? }
  inputs: Input[];              // { id, partId, name, mic, stand, phantom, own, note }。配列の順番がそのままCH番号
  gear: GearRow[];              // { id, memberId|null, item, own, power, note }
  monitors: MonitorReq[];       // { memberId, wedgePartId?, req }
  general: { light; sound; sync };
};
```

モックからの変更点が3つある。

- **チャンネルは独立した配列で持つ。** モックではパーツが入力を内側に持ち、パーツの並び順がCH番号になっていた。この形では、チャンネル表で行を並べ替えたいときにパーツの順番まで動かすことになる。`inputs` を独立させて `partId` で紐づければ、並べ替えは配列の操作だけで済む。パーツを消したら、紐づく入力も一緒に消す
- **人は名前ではなく `memberId` で参照する。** メンバー名を変えたときに、全帳票の表記が揃って変わるようにするため
- **曲番号・合計時間・電源の口数・CH番号は保存しない。** 毎回データから計算する（`model/derive.ts`）。保存すると元データとズレる余地が生まれるため

### 4. 保存: localStorage に自動保存し、JSONファイルで書き出し・読み込み

- 公演1件ごとに1つのキー（`setlist:show:<id>`）に保存し、一覧は別のキー（`setlist:index`）で持つ。画像を扱わないので容量の上限（約5MB）は問題にならない
- **JSONの読み込みはシステムの外から入ってくるデータなので、ここだけ zod で検証する。** localStorage から読むときも同じ検証を通す（古いビルドが保存したデータや、手で書き換えたデータがありうるため）
- 保存の失敗（容量不足、ブラウザがサイトデータを止めている）でもアプリは止めず、編集は画面上で続けられるようにし、失敗したことを知らせる。一覧のデータが壊れていたら、保存済みの公演から作り直す（`src/store/persistence.ts`）
- 編集は「元に戻す / やり直す」ができる。0.6秒以内の連続した編集（打鍵やドラッグ）は1回分にまとめる。別の公演を開くと履歴は消える
- 読み込んだデータが、存在しないパーツやメンバーを指していたら、その紐づけを外して読む（`parseShow`）。アプリでパーツやメンバーを消したときと同じ扱いで、帳票の見た目は変わらない。外さないと、編集画面の選択欄が保存されている値と違う選択肢を表示してしまうため
- ファイルの形式（1公演の JSON とバックアップの見分け方）は `src/model/backup.ts`、localStorage の読み書きは `src/store/persistence.ts` に分けている。前者は保存の仕組みと関係なく変わりうるため
- データ形式は一度外に出ると後から変えにくいので、`schemaVersion: 1` を最初から付けておく。形式を変えるときは、`schemaVersion` ごとの変換処理を `parseShow`（`src/model/show.ts`）の前段に足す

### 5. 印刷

- 方式: `@page` に名前を付けて縦と横を使い分け、帳票ごとに改ページし、印刷時も色を出す設定（`print-color-adjust: exact`）にする。Chrome で A4 縦2枚・横2枚になることは確認済み
- **印刷はシートごとに行うのを基本にする。** 縦と横が混ざった帳票を一度に印刷できるかはブラウザによって違う可能性があり、Safari と Firefox では確かめていないため。「全シート印刷」は Chrome 系のブラウザでだけ出す
- 演者用セットリストの文字サイズ自動調整は、ブラウザ上で実際に寸法を測る方式で行う。印刷用のシートは画面外に配置したまま常に描いておき、印刷前に寸法を測れるようにする
- 文字サイズの採寸は打鍵のたびに走るので、回数を減らしている。2回目以降は前回の文字サイズから探し始め（1文字の編集ではたいてい2回の採寸で決まる）、外れたら二分探索する。ページを開いて最初の採寸だけは、最大サイズを試してから二分探索する（前回の値がなく、最大付近のサイズを順に試すと大きな文字の採寸が重なって遅いため）。同じ内容のシートはプレビューと印刷用で2枚あるので、2枚目は直前の結果を使う。採寸し直すのは、このシートに描かれる内容（表示する項目・曲名などとヘッダー・フォント）が変わったときと、フォントのファイルを読み終えたときだけで、ステージ図や照明の編集では採寸しない。はみ出しは文字サイズが大きいほど増えるので、結果は1pt ずつ下げる方式と同じになる（読み込み直後と、同じページで曲を増減させたときの両方を e2e で照合している）

### 6. 画面構成

- 左に編集パネル、右にA4のプレビューを並べる。タブは「基本情報 / メンバー / セットリスト / ステージ / 機材・返し / 音響照明 / 取り置き / タイムテーブル / テキスト」の9つ
- 画面遷移のためのライブラリは入れない。どのタブを開いているかは Zustand の状態として持つ（画面が1枚なので）
- セットリスト: 1行1項目の表。dnd-kit で並べ替え、セルを直接編集する
- 音響照明: セットリストと同じ行を、照明・音響の列だけで見せる表
- ステージ: 置けるパーツの一覧と、SVGのキャンバス、選んだパーツの詳細欄の3つ。1単位ごとのグリッドに吸着し、回転は90°刻み。チャンネル表はステージのタブに並べて置く

### 7. テキストでの編集

- 基本情報・セットリスト（照明・音響の指示を含む）・全般要望を、Markdown に似たテキストで書いて取り込める（`src/model/text.ts`、画面は「テキスト」タブ）
- 対象をこの3つに絞った。メンバー・ステージ図・機材は位置やつながりの情報を持つので、文字で書くより画面で操作したほうが速いため。テキストを反映しても、この3つ以外は変わらない
- 反映はボタン（または ⌘/Ctrl+Enter）を押したときだけ行う。反映も「元に戻す」で取り消せる。書きかけの状態でフォームの内容が消えないようにするため。読めない行が1つでもあれば何も変えず、行番号付きでエラーを出す
- 反映していないテキストは、タブを切り替えても残る（ストアの `textDraft`）。別の公演を開くと消える。書き始めた後にほかのタブでフォームが変わったら、反映すると上書きされることを画面に出す
- 書き出してから読み込むと元の内容に戻る（テストで確認）。ただし、曲名に「|」、照明の雰囲気に「/」を含めると区切りと区別できない

### 8. 公演をまたいだ活用

- **曲ライブラリ**（`src/model/library.ts`）: 保存済みの公演から曲を集めて検索し、BPM・キー・尺・照明などの指示ごと今のセットリストに追加できる。曲名と原曲アーティストが同じなら同じ曲とみなし（全角・半角、大文字・小文字は区別しない）、日付がいちばん新しい公演の内容を使う。ライブラリ専用の保存領域は持たない（保存領域が二重になってズレるのを避けるため）
- **タイムテーブル**: 基本情報に開始時刻（`meta.startTime`、"HH:MM"）を入れると、各項目の開始時刻と終了予定の時刻を計算する。v1 を公開した後に足した項目なので、スキーマでは既定値を `""` にしてあり、古いデータもそのまま読める
- **共有リンク**（`src/share.ts`）: 公演データを gzip で圧縮し、URL の `#show=` 以下に入れる。`#` 以降はサーバーに送られないので、データは受け取った人にしか渡らない。開くと新しい公演として保存し、URL から `#` 以降を消す。連絡先も含めて公演の内容がすべてリンクに入る
- **バックアップ**: 全公演を `{ format: "setlist-generator-backup", version: 1, shows }` の形で1つのファイルに書き出す。「JSON読み込み」が1公演のファイルとバックアップを見分けて処理する。復元するとき、すでにある ID とぶつかったら新しい ID を振り、読めない公演は飛ばして件数を知らせる

### 9. 印刷する項目の切り替え

- 各シートに載せる列や欄を、公演ごとに ON/OFF できる（`show.performer` と `show.print`）。切り替えはプレビューの上の「表示する項目」で行い、そのとき表示しているシートの項目だけを出す。ヘッダーの公演名と連絡先は全シート共通
- 設定は公演データに保存するので、共有リンク・バックアップ・複製にも引き継がれる。v1 を公開した後に足した項目なので、無い場合は「表示する」として読み込む（古いデータは今までどおり印刷される）
- 演者用の表示設定（白黒反転・BPM・注釈）は、基本情報タブからこの欄に移した

### 10. 取り置きリスト

- 公演ごとに、チケットの取り置き（お名前・よみがな・枚数・担当メンバー・状態・備考）を持つ（`show.reservations`）。帳票「D 取り置き」は受付に渡す用で、キャンセルを除き、よみがなの五十音順に並べ、合計と担当メンバーごとの枚数を出す。よみがなを別に持つのは、漢字の名前だけでは読みの順に並べられないため（よみがなが空なら名前で並べる）
- メールやフォームで送るために、同じ内容をテキストでコピーできる。載せる列（よみがな・担当・備考）は帳票の「表示する項目」に合わせる
- **予約者の名前は第三者の個人情報なので、共有リンクには入れない**（`src/share.ts`）。共有リンクは会場スタッフや対バンに渡すことが多いため。JSON 書き出し・バックアップ・複製には入る（自分の手元に残すものなので）
- 取り置きのない公演（キャンセルだけの公演も含む）では、「全シート印刷」に白紙の取り置きリストを入れない
- メンバーを消しても予約は消さず、担当なしにする（予約そのものは残るべきなので）
- v1 を公開した後に足した項目なので、`reservations` がない古いデータは取り置きなしとして読む

### 11. 当日のタイムテーブル

- 入りから撤収までの当日の流れを、公演ごとに行の並びとして持つ（`show.timetable`）。帳票「E タイムテーブル」で印刷する。並び順は入力した順（ドラッグで並べ替え）で、時刻では並べ替えない。日付をまたぐ公演で順序が崩れないようにするため
- 「自分たちの出番」の行は時刻を保存せず、基本情報の開始時刻と持ち時間から毎回計算する（データモデルの「計算できるものは保存しない」方針どおり。開始時刻を変えるとタイムテーブルも変わる）
- 新しい公演では「よくある流れから作る」で、入り・リハーサル・開場・開演・自分たちの出番・終演・撤収の行をまとめて作れる。時刻は空なので自分で入れる
- メンバーや会場と共有するものなので、共有リンクにも入る
- タイムテーブルのない公演では、「全シート印刷」に白紙のタイムテーブルを入れない
- v1 を公開した後に足した項目なので、`timetable` がない古いデータは空のタイムテーブルとして読む

### 12. 帳票のフォント

- 帳票（プレビューと印刷）のフォントを公演ごとに選べる（`show.font`）。編集画面の文字は端末のフォントのまま。選べるのは端末のフォント（既定）と、Noto Sans JP・BIZ UDPゴシック・Zen Maru Gothic・Noto Serif JP・Dela Gothic One（`src/model/fonts.ts`）。公演データに入るので、共有リンク・バックアップ・複製にも引き継がれる
- **Web フォントは npm の `@fontsource` で自前配信する。** Google Fonts などの CDN を使わないのは、CSP の `font-src` / `style-src` を外部に開かずに済み、利用者の閲覧が第三者に送られないため。代償として、ビルド結果が約 48MB・約 2,000 ファイルになる（古い形式の woff も含むため。ブラウザが取得するのは woff2 だけ）
- フォントの CSS は選んだときにだけ読み込む別のファイルにしてある。CSS は文字の範囲ごとに分かれているので、ブラウザは帳票で使う文字の分だけをダウンロードする。端末のフォントのままなら、追加の通信はない
- フォントのファイルは `data:` URL にしない（`vite.config.ts` の `assetsInlineLimit`）。CSP の `font-src 'self'` で止まるため
- 読み込みが終わるまでは端末のフォントで表示し、終わったら演者用の文字サイズを測り直す。印刷は、印刷する全文字の全ウェイトを読み終えるまで待ってから行う（その間、ボタンは「フォントを準備中…」になる）。読み込めなかった文字は端末のフォントで印刷し、そのことを知らせる
- そのフォントにないウェイト（太さ）は、ブラウザが作る疑似的な太字ではなく、いちばん近い実在のウェイトで描く。端末のフォントのときは今までどおり
- v1 を公開した後に足した項目なので、`font` がない古いデータは端末のフォントとして読む。このバージョンが知らないフォント（新しいバージョンのデータ）も端末のフォントとして読み、公演全体が読めなくなるのを避ける
- フォントはすべて SIL Open Font License 1.1

### 13. 公開: GitHub Pages

- `main` への push で GitHub Actions がテストとビルドを行い、`dist/` を Pages に公開する（`.github/workflows/deploy.yml`）
- `vite.config.ts` の `base: "./"` で相対パスにしてあるので、リポジトリ名が変わっても動く
- **ビルドした HTML には CSP を meta タグで入れる**（`vite.config.ts`）。共有リンクで他人のデータがこのページに入るので、実行できるスクリプトを同梱のものだけに限る。GitHub Pages ではレスポンスヘッダーを設定できないため meta タグにした。開発サーバーはホットリロードにインラインのスクリプトを使うので、ビルドのときだけ入れる。eval も禁じるので、zod には eval を使わない設定（`jitless`）をしている。アプリの全機能で CSP 違反が出ないことは e2e で確かめている

## 今回やらないこと

サーバーやアカウント、クラウド同期、英語表示、オフラインで使えるようにする対応（PWA）、スマホでのステージ図編集（スマホは閲覧と印刷のみを想定）、照明機材の種類の指定、ステージの大きさの変更（幅160×奥行44で固定）。

## この計画が崩れる条件

- **縦と横が混ざった印刷やSVGの描画が、Safari / Firefox で Chrome と大きく違う場合。** その場合は帳票ごとに単独で印刷する方式に寄せるか、PDFを直接生成する方式（pdf-lib など）に切り替える。手順1で、各ブラウザから印刷して確かめれば分かる
- **主な利用者がスマホで編集する場合。** ステージ図の編集画面と、左右に並べる画面構成の前提が変わる
